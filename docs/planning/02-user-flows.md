## 0. 설계 원칙 요약

| # | 원칙 | 적용 |
|---|------|------|
| UX-1 | **왼쪽 메뉴 대시보드** | 모든 로그인 화면은 왼쪽 메뉴 4개(커리어 / 기업 JD 관리 / 모의 면접 / 지원 현황)를 가진 셸(L-01) 안에 있다. 로그인 후 첫 화면은 항상 커리어(S-08). v3의 홈(S-07)은 폐기 |
| UX-2 | **데이터는 두 곳에만 산다** | 커리어(사용자당 1개)와 지원 프로젝트(여러 개). "모의 면접" 메뉴와 "지원 현황" 메뉴는 지원 프로젝트 데이터를 다르게 보여 주는 **보기이자 진입점**이다. 면접 세션은 항상 지원 프로젝트에 속하고, 전형 단계는 지원 프로젝트의 속성이다 |
| UX-3 | **순서를 강제하지 않는다** | 어느 메뉴·기능도 다른 것의 완료를 요구하지 않는다. 인사이트는 선행 조건이 아니다. 연결은 데이터와 복귀 경로뿐이다(C-09·C-10) |
| UX-4 | **커리어 입력은 두 길** | 폼 직접 입력(S-09·S-10·S-34·S-35) 또는 AI 작성 대화(S-36). 어느 쪽이든 결과는 같은 커리어 데이터다. 대화에서 폼으로 언제든 바꿀 수 있다. AI는 사용자가 말하지 않은 사실을 쓰지 않고, **사용자가 확정해야** 커리어 데이터가 바뀐다 |
| UX-5 | **근거 표시는 하나의 패턴** | 인사이트·서류·면접 평가 모두 C-01 근거 칩 + C-02 근거 패널. v4부터 근거 단위가 STAR 필드까지 내려간다("상세 내용 · 행동"). AI 작성 대화의 정리 결과는 같은 모양의 **출처 발화 칩**(C-15)을 쓴다 |
| UX-6 | **AI는 사용자가 누를 때만 실행** | 요건 추출만 키가 있을 때 JD 생성 직후 자동(D-30). 인사이트·초안·면접·AI 작성 대화는 버튼으로 시작하고, 버튼 옆에 **지금 쓰는 공급자·등급 배지**(C-19)를 둔다. 서비스 횟수 안내는 없다(BYOK, D-34). 지원 현황 팝업은 AI를 실행하지 않는다. 키를 연결한 순간 일괄 실행하지 않는다 |
| UX-10 | **AI는 선택 확장 기능 (BYOK)** | 커리어(폼), 기업 JD 등록·관리(공고 원문), 지원 현황 보드는 **키 없이 완결**된다. AI 진입점은 키가 없으면 하나의 잠금 패턴(C-18)을 보이고, 거기서 설정 > AI 연결로 갔다가 원래 화면으로 돌아온다. 가입·온보딩에는 키 단계를 넣지 않는다(D-35) |
| UX-11 | **비용·한도는 공급자 것** | Resumate는 서비스 한도·남은 횟수를 보여 주지 않는다. 대신 사용량 미터(S-42, 예상치)와 공급자 한도·오류 안내(C-20)만 둔다. 품질·안전 목적 제한(AI 작성 대화 메시지 40개 등, D-34)은 유지한다 |
| UX-7 | **입력은 잃지 않는다** | 폼·상세 내용·자소서 문항·면접 답변지 자동 저장, AI 작성 대화는 기록과 정리 결과를 보존해 이어 한다. 필수 필드가 덜 찬 커리어 항목은 `status = 'draft'`로 저장되고 AI 근거에서 빠진다 |
| UX-8 | **드래그 없이도 모든 조작 가능** | 지원 현황 보드는 드래그앤드롭과 같은 일을 카드 메뉴 "단계 이동"으로도 할 수 있다(키보드·터치·스크린 리더) |
| UX-9 | **데스크톱 우선** | 모바일은 열람, 면접 답변, 보드 단계 이동, AI 작성 대화까지 완결 가능해야 한다 |

- "폼으로 전환"은 사용자가 옮기기를 확인한 순간 RPC `hand_off_writing_chat(writing_chat_id)`가 정리 결과를 커리어 테이블에 쓰고(완료 판정대로, 대부분 `draft`) `writing_chats.status = 'handed_off'`가 된다. 이후는 폼 자동 저장 규칙(D-UX-11 (a)). 수락하지 않은 `needs_review` 필드는 옮기지 않는다(R-27).
- 키 필요(F-P1-13). 모든 시작점은 먼저 활성 공급자 키를 확인하고, 없으면 C-18 잠금을 보인다. 키가 무효·삭제돼도 진행 중 대화와 정리 결과는 보존·열람되고, 새 메시지를 보낼 때 C-20 안내가 나온다(D-36).
- 서비스 횟수 제한은 없다(D-34). **메시지 상한 40개(사용자 + AI 합계, 시작 인사는 제외)**는 품질·안전 목적으로 유지되며, 닿으면 저장 또는 새 대화로 이어 가게 한다(A5, 확정 2026-11-05 (사용자)). 토큰은 사용량 미터의 "AI 작성 대화"로 집계된다.
- **그만둔 대화 재개 (A6, 확정 2026-11-05 (사용자))**: `abandoned` 대화는 사용자가 "다시 이어 하기"를 누르면 `active`로 돌아가 기록·정리 결과·수락 상태·확정 소속이 그대로 복원된다. 자동 정리(프로젝트에 묶이지 않은 대화는 마지막 활동 후 90일 `[가정]`) 전까지만 가능하다. 재개는 사용자 동작으로만 일어나고, 재개 자체는 AI를 부르지 않는다(키 없이도 재개·열람 가능, 새 메시지만 키 필요). 대화를 `abandoned`로 만드는 진입점은 S-36·S-08의 "대화 그만두기"(사용자 전이 `active → abandoned`, 데이터 모델 v4.2 2.5)로 둔다. 진입점 위치는 `[가정]`.

#### C-04 스트리밍 출력

경력기술서(블록), 자기소개서(문항, 근거 선택 먼저), 면접 질문(차례로 채움), **AI 작성 대화 응답(첫 글자 3초, 완료 10초)**. 중단은 `ai_jobs.cancel_requested_at`. 이탈 시 서버가 끝까지 생성·저장 `[가정]`.

- **서류 스트리밍 이벤트 순서 (AI-04, 구현 반영)**: `sources_selected`(사용한 경력·프로젝트 카드 먼저) → 블록 스트리밍(`block_started` / `block_delta` / `block_completed`) → (글자 수 보정이 필요할 때만) `adjusting_length`("글자 수 맞추는 중", 보정 전 글자 수·제한·기준 표시) → **`validated`** → `done`.
- **블록 확정 시점**: 스트리밍 중 블록은 **임시 표시**다(블록 id가 아직 확정되지 않음). `validated`가 오면 화면은 그 문항(경력기술서는 초안)의 블록을 **통째로 교체**한다. 근거 칩·자리 표시·검증 배지·"생성 직후 안내"(S-19)는 `validated` 뒤에 붙는다. 그 전에는 편집·복사를 막고 "마무리 중"으로 보인다. 경력기술서(AI-03)도 같은 방식이다(블록 id는 `validated`에서 확정).

#### C-20 한도·오류 안내 (v5 신설, F-AI-08 — 기존 ST-AI-FAILED 대체)

- **자동 재시도 규칙** (AI 명세 v4.3 C-11.3, 유료·무료 같음): `rate_limited` 호출당 최대 4회(공급자 `retry-after`, 없으면 2·4·8·16초) / `provider_unavailable` 최대 2회(2·4초) / `schema_invalid`·`timeout` 1회 / 그 밖 0회. 한 작업의 재시도 대기 합계는 최대 120초. 스트리밍은 첫 토큰 전에만 재시도한다. 최종 실패 시 `ai_jobs.retry_after`가 채워지고 "다시 시도" 버튼이 그 시각까지 카운트다운한다. 무료 등급은 호출을 간격을 두고 순차로 보낼 뿐 재시도 규칙은 같다.
- **요청 안에서 끝나는 경로의 대기 (AI 명세 v4.3 C-11.3, A14 확정 2026-11-05 (사용자))**: 비동기 작업(인사이트·면접)만 위 대기 재시도를 한다. **AI 작성 대화 턴과 서류 스트리밍**은 첫 토큰 전 즉시 재시도(`schema_invalid`·`timeout`)만 하고, 분당 한도·공급자 장애처럼 기다려야 하는 원인은 **바로 실패**로 보인다 → 대기 시간 안내("{N}초 뒤 다시 보낼 수 있어요") + `retry_after`까지 카운트다운하는 "다시 보내기"/"다시 시도". **요건 추출(동기)**은 5초 이하 대기만 요청 안에서 기다리고, 더 길면 같은 방식으로 실패를 보인다. 무료 등급 호출 간격(약 6초)은 요청 안에서 기다리므로 "조금 느릴 수 있어요" 안내로 충분하다.
- **다시 시도의 공급자 (A1, 확정 2026-11-05 (사용자, A1 변경))**: **다시 시도를 포함한 모든 재실행은 버튼을 누른 시점의 활성 공급자·등급으로 돈다.** 경우를 나누지 않는다(이전의 "같은 작업 행 다시 시도 = 처음 공급자" 해석은 폐기, R-48).

#### 실행 버튼 공통 규칙 (v5)

- 모든 AI 실행 버튼(인사이트 생성, 요건 정리하기, 경력기술서 생성, 자소서 생성·다시 생성, 면접 시작·제출, 다시 채점, AI 작성 대화 시작) 옆에 **C-19 공급자·등급 배지**를 둔다.
- 키가 없으면 버튼 자리가 C-18 잠금(인라인형)으로 바뀐다. 키가 무효면 버튼은 보이되 누르면 C-20 `key_invalid` 안내.
- **횟수·남은 사용량 표시는 없다**(v4.2b의 "이번 달 {N}회 남음 · 이 작업으로 {k}회 사용", AI 작성 대화 "{N}/10회"는 삭제, D-34). 비용 감각은 사용량 미터(S-42)가 맡는다.
- 다시 생성·다시 채점처럼 같은 일을 또 하는 버튼에는 "다시 하면 공급자 토큰을 다시 써요" 한 줄을 붙인다(NFR-AI-08). 동일 입력 결과가 있으면 새로 호출하지 않고 기존 결과를 보여 준다.
- 품질·안전 목적 제한은 유지하고 "한도"라는 말을 쓰지 않는다: AI 작성 대화 메시지 40개, 입력 길이 상한, 같은 대상에 같은 AI 작업 동시 실행 1개("이미 만들고 있어요"), 지원 프로젝트당 작성 중 면접 1개(D-34). 서버 남용 방지 제한에 걸리면 "잠시 후 다시 시도해 주세요"로만 보인다 `[가정]`.

### S-08 커리어 (기본 첫 화면)

- 목적: 커리어를 **연도 > 경력/교육 > 프로젝트 > 상세 내용** 계층으로 한눈에 보고, 어디서든 폼 또는 AI 대화로 입력한다. J-1의 완료 지점(F-P1-09).
- 관련: F-P1-01~05, F-P1-09, F-P1-13, F-P1-14, F-P1-15, F-COM-04. 진입: 로그인, L-01 메뉴, C-09, C-02 / 이탈: S-04, S-09~S-12, S-34~S-36

**연도 묶음 규칙 (D-22 (b) 권고)**
- 경력·교육은 활동한 **모든 연도**에 나타난다(`start_month`~`end_month`, 재직·재학 중이면 올해까지). 데이터는 하나, 표시만 반복.
- 각 연도 아래에는 그 해에 **시작한** 프로젝트만 보인다(`projects.start_month`의 연도). 프로젝트 기간이 비어 있으면 소속 경력·교육의 시작 연도에 둔다 `[가정]`.
- 그 해에 시작한 프로젝트가 없는 경력·교육은 **접힌 머리**만 보인다(회사명·기간).
- 독립 프로젝트(소속 없음)는 해당 연도의 **"기타 프로젝트"** 묶음에 둔다. 기간도 없으면 맨 아래 "연도 미정" 묶음 `[가정]`.
- 최신 연도가 위. 연도·경력/교육·프로젝트·상세 내용 각 단계를 접고 펼 수 있다. 접힘 상태는 브라우저에 기억 `[가정]`.

  - 메시지 상한 40개(D-34 유지, 시작 인사 제외 — A5): 닿으면 "대화가 길어져 정리 정확도가 떨어질 수 있어요. 지금까지 내용을 저장하거나 새 대화로 이어 가세요" + [저장] / [폼으로 전환] / [새 보강 대화]. 월간 횟수 한도(v4.2b U-8 "월 10회")는 **폐기**(BYOK, D-34).

### S-14 기업 JD 추가

  - `application_projects.deadline`.
  - 새 지원 프로젝트의 `stage = 'before_apply'`(지원 전).
  - 진입이 S-39면 저장 후 S-39로 돌아가 "지원 전" 열 맨 위에 카드 + "열기" 토스트.

  - (v5.3) **글자 수 표시 (A12)**: 문항마다 "현재 {n}자 / 제한 {limit}자({공백 포함·제외})". 제한을 넘었지만 110% 이내라 보정하지 않은 경우 "제한보다 {n − limit}자 많아요. AI 보정 범위(최대 10% 초과) 안이라 그대로 두었어요. 제출처 제한을 확인해 주세요". 편집본(`edited_content`) 기준으로 실시간 다시 센다.
  - (v5.3) 숫자 확인: 근거 없는 숫자는 다시 만들지 않고 `[수치 확인 필요]` 자리 표시 + 검증 배지(C-08)로 보인다(AI 명세 v4.3 C-3 V-5 예외). 경력기술서 블록은 초안당 최대 500개·블록당 5,000자, 섹션 최대 30개 `[가정]`(구현 값).

### S-33 면접 답변지

v3와 같음 + 다음:

- **답변 편집 가능 조건**(데이터 모델 RLS): `interview_answers.status = 'draft'` **그리고** 세션 `submitted_at is null` **그리고** 세션 `generation_status = 'ready'` **그리고 세션 `status = 'in_progress'`**. 화면은 이 조건이 아닐 때 답변란을 읽기 전용으로 보여 준다(생성 중: "질문을 준비하고 있어요", 제출 후: S-22로).
- **그만둔 세션 (A8, 확정 2026-11-05 (사용자))**: `status = 'abandoned'`면 제출 전이어도 답변을 고칠 수 없다. 상단 "그만둔 면접이에요. 답변은 볼 수만 있어요" + "이 기업 JD로 새 면접 시작"(→ S-20). 제출 버튼 없음.
- 질문 근거: 질문마다 근거 칩(C-01, `evidence_links` owner `interview_question`)을 제출 전에도 보인다. 질문 의도·좋은 답 신호는 제출 후 S-22에서만(구현 반영).
- 질문 유형 라벨은 세션 `interview_type`에서 가져온다(`interview_questions.question_type` 삭제).
- 질문 저장 시 빈 답변 행이 함께 생기므로 질문마다 답변란이 항상 있다.
- 제출은 RPC `submit_interview_session` → 서버가 공백만 있는 답변을 `unanswered`로 확정, `interview_sessions.submitted_at`, `unanswered_count` 기록.
- 남은 질문 다시 만들기(일부 생성 실패 시): **현재 활성 공급자**로 돈다(C-20 "다시 시도의 공급자", A1 변경), 버튼 옆 C-19 배지는 활성 공급자. 공급자 토큰을 다시 쓴다는 한 줄. (D-DM-07 무차감 규칙은 차감 개념 폐기로 삭제, D-34)
- **(v5) 키와 제출**: 답변 작성·자동 저장은 키 없이 가능. **제출은 채점(AI)이므로 키 필요** — 키가 없으면 제출 버튼 자리에 C-18 인라인("제출하면 연결한 AI로 채점해요. 작성한 답변은 저장돼 있어요"), 키가 무효면 C-20 `key_invalid`. 질문 생성 중 키 문제로 실패하면 C-20을 생성 영역에 보이고 이미 저장된 질문·답변은 보존(D-36).

### S-22 면접 결과

v3 구조 유지 + 점수 슬롯 컬럼 확정. (v5) 결과 상단에 C-19 결과 배지(채점한 공급자·모델). 채점 실패 답변의 "다시 채점"은 키 필요(없으면 C-18 인라인), "다시 채점하면 공급자 토큰을 다시 써요" 한 줄. 공급자 원인 실패는 C-20(채점 끝난 답변 카드는 보존). 결과 열람은 키 없이 가능.

**다시 채점 (v5.3, A9, 확정 2026-11-05 (사용자))**

| 요소 | 표시/동작 | 비고 |
|------|-----------|------|
| 버튼 | 세션 상단 하나: **"실패한 답변 {n}개 다시 채점"** + C-19 배지(**현재 활성 공급자**) + "다시 채점하면 공급자 토큰을 다시 써요". 답변 카드의 "다시 채점"도 같은 동작(세션 단위) | 평가 성공이 없는 응답 답변만 다시 평가한다. 이미 채점된 답변은 다시 부르지 않는다. 다시 채점은 현재 활성 공급자로 돌고 `evaluation_provider`·`evaluation_model`을 덮어쓴다(C-20 "다시 시도의 공급자", A1 변경). 이 화면에는 같은 행 다시 시도 버튼을 따로 두지 않는다 |

| 진행 중 | 세션 `status = 'evaluating'`, 점수·완료 시각을 비우고 C-03(`prepare` 채점 준비 중 → `evaluate` n/N → `summarize` → `score` → `complete`(문구 없음, `score` 문구 유지)) | 단계 순서는 AI 명세 v4.3 C-6 |

#### C-17 점수 표시 규칙 (신설)

| `score_status` | 세션(`interview_sessions`) | 질문별(`interview_answers`) |
|----------------|---------------------------|-----------------------------|
| null | (제출 전) 표시 안 함 | 표시 안 함 |
| `pending_method` | "점수 산정 방식 준비 중" | "점수 준비 중" |
| `scored` | `score_value` / `score_max` + `score_rationale`(펼치기) + "반영 질문 {score_counted_count}개" | `score_value` / `score_max` + `score_rationale` |
| `unanswered` | (세션에는 없음) | "미응답" |
| `not_scored` | "점수를 계산하지 못했어요". 단 `unanswered_count = question_count`(응답 0개)이면 **"답변이 없어 평가할 내용이 없어요"** + "새 면접 시작하기" | "채점 실패" + 다시 채점 |

- 점수 근처에 고정 고지: "입력한 답변 기준 연습 점수예요. 합격 가능성을 뜻하지 않아요"(NFR-AI-03).
- `score_method_version`은 화면에 직접 표시하지 않고, 지난 세션과 방식이 다르면 "다른 산정 방식으로 계산된 점수예요" 안내 `[가정]`.
- 세션 헤더에 `unanswered_count`, "다룬 보완 요건"(`weak_requirement_ids` → 요건 `content`), 데이터 부족 시 `data_sufficiency` 안내.
- 답변별 카드의 질문 유형 라벨은 세션 `interview_type`.
- 항목별 등급(`answer_evaluations.result.criteria[]`)과 다음 연습은 D-14 결과에 따라 표시(v3와 같음).

- 목적: 모든 기업 JD의 면접 세션을 모아 보고, 기업 JD를 골라 새 면접을 시작한다. 세션은 계속 지원 프로젝트에 속한다.

|----------|------------------|------|------|

| 필터 | 기업 JD(`application_project_id`), 유형(`interview_type`), 상태, 실행 공급자 `[가정]` | | |
| 세션 목록 | 기업 JD 이름(`application_projects.name`), 유형, `created_at`, 상태(작성 중 / 채점 중 / 완료 / 채점 실패 / 그만둠), 세션 점수(C-17), 새 결과 표식, **실행 공급자**(C-19 "면접 세션의 실행 공급자" 규칙) | → S-22 / S-33, 행 메뉴: 삭제(C-05), 기업 JD로 가기(S-31), 채점 실패 행은 "실패한 답변 다시 채점"(S-22와 같은 동작, 현재 활성 공급자. 채점 중 행의 진행은 S-22와 같이 `prepare` 채점 준비 중 → `evaluate` → `summarize` → `score` → `complete`) | 최신순. **그만둠(`abandoned`) 세션은 목록 아래쪽 "그만둔 면접" 묶음**에 남기고 삭제할 수 있다(PRD F-P3-15 v3.1). 그만둔 세션은 열면 읽기 전용(S-33, A8) |

### S-39 지원 현황 보드 (신설, F-ST-01~05)
