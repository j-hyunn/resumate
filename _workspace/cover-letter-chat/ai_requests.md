### data-architect (데이터 모델 04)

**가장 먼저 필요한 것: 아래 1~4의 이름.** 이 문서는 제안한 모양을 `[가정]`으로 쓰고 있고, DM v4.13이 확정한 이름으로 바꿉니다.

1. **`structured_draft`의 서류 모양** (CL-3·CL-9, AI-03·AI-04 저장): `target = 'career_description'` / `'cover_letter'` + `schema_version: 1`로 구분하는 데 동의합니다(DM 사전 조사 3장 초안과 같습니다). 모양에서 AI 쪽이 요구하는 것은 **슬롯이 여러 개**라는 점입니다 — AI-13의 `deliverable.body` 하나와 달리 **AI-12의 필드 객체 모양**(슬롯별 `{value, blocks[], evidence[], rev, review, review_reason, applied_at, applied_rev}`)에 가깝습니다. 키 이름은 `document.sections[]` / `document.questions[]`로 서류 종류별로 나누는 쪽에 **동의**합니다(한 이름 `items`로 통일하면 블록·근거 모양이 같아도 `char_limit` 같은 자소서 전용 키가 섞입니다).
2. **슬롯 키와 `evidence_links` 소유자 키** (CL-5, C-3): `owner_type = 'draft_section'`을 폐기하고 **서류 정본 행을 가리키는 새 값**이 필요합니다 — 제안 **`application_document`**(`owner_id` = 정본 행 id). `item_key`는 **`{slot}.{block_id}`**(예 `s_3.b2`, `q_2.p1`), 근거 선택 이유는 **`{slot}.sources.{n}`**입니다. 슬롯 접두사를 **반드시** 두세요 — 한 서류 안에 섹션·문항이 여럿이라 블록 id만으로는 유일하지 않고, AI-13의 `block_id`(`b2`)와도 섞입니다. 슬롯 키 자체는 `s_{n}`·`q_{n}`(사람이 읽는 안정 키)이든 uuid든 AI 쪽은 상관없지만, **모델 입력·출력에 들어가므로 짧아야** 합니다(uuid면 턴당 입력이 수백 토큰 늘고 모델이 틀리기 쉽습니다) — **짧은 키 + 정본의 uuid 매핑**을 권고합니다. 기존 행 처리는 **SD-A19의 `profile` 패턴**(기존 행·라벨 유지, `source_deleted_at` 소급 없음, CHECK 유지 + insert 트리거만 거부, 칩은 "원본으로 이동"만 비활성)으로 **권고**합니다 — C-3에 그렇게 적었습니다.
3. **문항 정의의 저장 위치** (CL-8·CL-9, Q-AI-2): **문항 정의(문구·`char_limit`·`count_basis`·`template_key`·`user_note`)는 `structured_draft` 밖, 서류 정본 행에** 둡니다. 대화·키 없이도 존재·편집돼야 하기 때문입니다(CL-8은 `[가정]`이 아니라 확정). `structured_draft`에는 **문항 키 참조 + 답변 본문 제안·근거**만 담습니다. 경력기술서의 **섹션 순서도 정본 쪽**입니다(모델은 `section_order_proposal`로 제안만 하고 정본 순서를 덮지 않습니다).
4. **`user_note` 근거의 `source_id`** (C-3): 지금은 `draft_sections.id`입니다. **정본 행의 문항 키**를 가리키는 모양이 필요합니다(정본 행 id + 문항 키 조합이든 문항별 uuid든 DM이 정해 주세요).
5. **`facts[].slot` 값 목록** (DM 요청 2에 대한 회신): 서류 대화의 슬롯은 **고정 목록이 아니라 그 서류의 섹션·문항 키**입니다 — 경력기술서는 `s_{n}`(경력·교육·독립 프로젝트 단위), 자소서는 `q_{n}`(문항). AI-13처럼 종류별 고정 슬롯 키 목록(`contribution` 등)을 두지 않습니다. 사실의 **성격**은 `slot` + `project_ref`로 충분합니다(AI-03 출력 스키마 ② 참고).
6. **AI-11 결과 저장 위치** (DM 요청 6, D-57): `ai_jobs.output`(`draft_source_ranking`) 보관은 그대로 두고, 복사 대상을 **`structured_draft`의 `document.source_ranking = {origin, items[], generated_at}`**으로 바꿉니다 — `drafts.options.ranking`·`selection_origin`은 폐기에 **동의**합니다. `selection_origin` 3값(`insight`/`ai_ranking`/`user`)은 그 메타의 `origin`으로 유지합니다.
7. **`ai_jobs.job_type`** (DM 요청 9, A-25 · CL-A8): **`career_description`·`cover_letter`를 턴 단위 `job_type`으로 그대로 유지하기를 권고**합니다(`writing_chat_turn`으로 합치지 않습니다). 이유는 사용량 `feature` 판정을 **한 컬럼으로** 끝내기 위해서입니다 — 합치면 판정이 `call_key` 문자열에 의존하게 되어 C-13.1의 두 행("자기소개서 작성 AI 채팅" ↔ "프로젝트/산출물 작성 AI 채팅")이 섞입니다. 그 결과 **새 조합이 생깁니다**: `job_type = 'career_description' | 'cover_letter'`인데 **`target_type = 'writing_chat'`**이고 **`application_project_id`는 채워집니다**(서류는 지원 프로젝트 안의 기능). `job_type`의 뜻도 "초안 1건 생성"에서 **"대화 턴 1회"**로 바뀝니다. **"대화 턴"을 세는 뷰·분석은 `job_type in ('writing_chat_turn','career_description','cover_letter')`로 봐야 합니다** — C-13.1 아래에 조합 표를 넣었습니다. `draft_source_ranking`(AI-11)은 그대로입니다.
8. **사용량 `feature`는 그대로입니다** (CL-A8 — 확정): 저장 8값 변경 없음, 표시 합산(`career_description` + `cover_letter` → "자기소개서 작성 AI 채팅") 변경 없음, 조회 RPC는 계속 저장 8값을 돌려주고 합산은 화면 매핑 상수 한 곳(DM 2.9.5·C-13.1). **서류 대화의 정리·응답·초안·보정 호출 모두 같은 두 값으로 기록되고 `writing_chat`으로 새지 않습니다.** `call_key`는 `career_description.turn.{n}.{extract|reply|compose}` / `cover_letter.turn.{n}.{extract|reply|compose|adjust_length}` / `career_description.rank`(AI-11)입니다.
9. **저장 RPC와 반영 기록** (CL-2·CL-9): `save_project_page`·`save_project_deliverable`에 대응하는 **서류 저장 RPC**가 필요합니다. `p_applied_proposals`는 **슬롯이 여러 개**라 **`[{writing_chat_id, slot, rev}]`** 모양(AI-12의 `field`에 대응)이고, `skipped.reason` 6종(`not_found`·`already_applied`·`proposal_changed`·`needs_review`·`invalid_entry`·`mark_failed`)·`stale_write`(409)·`field_too_long`(400)은 같은 모양으로 두세요. **같은 트랜잭션에서 섹션(문항) 근거를 `evidence_links` 행으로** 넣어야 합니다(A24 — AI 경로는 `evidence_links`에 직접 INSERT하지 않습니다). 자소서를 **문항별 저장으로 쪼갤지는 ux-planner 회신에 따릅니다**(PRD Q-PRD-2).
10. **AI 쓰기 경로** (NFR-AI-05): `app_ai_writer`는 **`apply_structured_draft_patch`로만** `structured_draft`를 바꾸고 **서류 정본 테이블 쓰기 권한이 없습니다**. 서류 본문·문항 확정은 사용자 세션의 저장 RPC만입니다. 대화 시작 RPC(`start_writing_chat`·`start_deliverable_writing_chat`에 이어지는 서류용)의 `p_form_snapshot`은 **시작 인사 분기용**이고 저장하지 않습니다(본문 없음 / 일부 / 전부 채워짐 / 요건 추출 전).
11. **섹션별 `base_body_hash`** (DM 요청 5, D-25): **섹션(문항) 단위로 두기를 권고**합니다 — 서류는 슬롯이 여럿이라 서류 전체 해시로는 "내가 고친 문항"과 "다른 문항"을 구분할 수 없습니다. 공백 정규화는 AI-13의 OD-P5 규칙(같은 함수)을 그대로 쓰고, "기준 본문이 바뀐 경우" 안내도 **그 슬롯에만** 냅니다.
12. **`draft_count` 상한** (DM 요청 4, Q-DM-8): **대화 전체 6회**로 두기를 권고합니다(섹션별 6회가 아닙니다). 이유는 상한의 목적이 **사용자 비용 보호**이고(7.4) 섹션·문항이 10개면 섹션별 6회는 60회가 되어 보호가 사라집니다. 상한에 닿으면 "새 대화에서 이어 하기"입니다(정본이 대화 밖이라 끊기지 않습니다, CL-9). 이 값은 **`[가정]`**이고 CL-Q1에 묶여 있습니다.
13. **글자 수 보정의 저장 위치** (DM 요청 7, D-59): 보정은 **초안 턴 안의 `adjust_length` 단계**이고 `requestedAction`이 아니라 **`style`**로 받습니다(`shorter` / `fit_length`). `char_count`·`char_limit_at_generation`·`char_adjust_needed`·`correction_applied`는 **그 문항 제안**(`structured_draft`)에 적습니다. `call_key`는 위 8번.
14. **섹션 근거를 `evidence_links`에 넣는 것** (DM 요청 10, D-4·D-50): **넣습니다 — 산출물 대화(AI-13)와 다른 것이 맞습니다.** 산출물 본문은 그 자체가 커리어 데이터(근거의 원본)이지만, **서류 본문은 커리어 데이터를 인용한 결과물**이라 "이 문장이 어느 경력·프로젝트에서 왔는가"가 사용자에게 보여야 합니다(근거 칩 C-01, F-DOC-03·08, 면접 연결). **V-8(배운 점 근거 거부)·숫자 가드는 제안 단계(초안 턴의 서버 검증)에서** 돌고, 저장 단계는 통과분을 `evidence_links`로 옮기기만 합니다 — 저장 RPC가 근거 검증을 다시 하지 않습니다(검증 입력인 팩·인용 원문이 저장 시점에 없습니다). 다만 **`job_competency` 문항의 `learnings` 근거 거부**(D-49)처럼 **값 목록으로 판정되는 규칙은 저장 RPC에 남겨도 됩니다**(CHECK 수준의 마지막 안전망).
15. **`input_hash` 재사용 폐기 확인** (DM 요청 8): **맞습니다** — 서류 생성의 "같은 입력이면 호출 안 함"이 없어집니다(대화 턴에는 재사용이 없습니다). `drafts.input_hash`와 `(user_id, application_project_id, input_hash) where ready` 인덱스가 함께 폐기되고, **재사용이 남는 것은 AI-11**(`career_snapshot_hash` + `requirements_hash`)뿐입니다.
16. **`composing` 폐기** (CL-A6): 동의합니다. `drafts.status` 5값·`partially_failed`가 함께 없어지고, **초안 턴 실패는 상태가 아니라 "제안을 바꾸지 않음"**입니다(AI-03 실패 유형). "서류 초안 수"는 **내용이 있는 서류만** 세는 쪽에 동의합니다.
17. **`get_data_readiness().features.draft`**: 판정값은 유지하되 **"기능 진입 차단"이 아니라 "초안 제안 차단"**으로 읽히게 정의해 주세요(C-1 게이트 표, PRD F-DOC-11 (6) `[가정]`). 대화 자체는 D-01 미달에도 열립니다.
18. **공급자·모델 배지의 자리** (UX #36): `drafts.provider`·`model`·`model_tier`가 없어집니다. **제안 쪽은 그 턴의 `ai_jobs`**에서, **정본 쪽은 반영된 제안의 메타**에서 읽는 모양을 권고합니다. "문항마다 공급자가 다를 수 있다"는 전제는 **유지됩니다** — 한 대화 안에서도 사용자가 활성 공급자를 바꾸면 다음 턴부터 새 공급자이고(F-AI-03 (2)), 문항은 턴을 나눠 만들어지므로(CL-10) 같은 서류 안에서 문항별 공급자가 다를 수 있습니다.

### ux-planner (UX 02)

1. **응답 모드 — 서류 2종 모두 스트리밍 대화 턴(SSE)이고 이벤트 이름을 AI-13 쪽으로 통일합니다** (UX 질문 AI-1, CL-6·CL-A7): 질문 턴 `turn_started` → `reply_delta` → `reply_done` → `draft_patch` → `draft_flags` → `turn_done` / 초안 턴 `turn_started` → `draft_patch` → **(자소서는 문항마다) `sources_selected`** → `draft_started` → `draft_block` → **(보정 시) `adjusting_length`** → `draft_done` → `reply_done` → `turn_done`. **v4.12의 `block_started`/`block_delta`/`block_completed`/`validated`/`done`은 서류에서 폐기**하되, "**모델 `block_id`를 믿지 않고 `draft_done`에서 블록을 통째로 교체**"하는 규칙은 그대로입니다(옛 `validated`가 하던 일). `sources_selected`·`adjusting_length`는 **초안 턴 안의 이벤트로 남습니다**(CL-A4로 글자 수 보정이 유지되므로).
2. **턴 종류는 2종** (AI-2): 질문 턴 / 초안 턴입니다. **제안 단위는 슬롯** — 경력기술서는 **섹션 단위**(서류 전체 1개가 아닙니다), 자소서는 **한 턴 최대 3문항**(CL-10). [반영] 버튼은 **슬롯마다** 있고, 확인 줄의 일괄 [반영 (n)]은 AI-12 모양입니다. 산출물의 "교체/덧붙이기 2버튼"이 아닙니다.
3. **첫 턴 제안 문구** (AI-3, CL-10 확정): 자소서는 "모아 둔 커리어로 **먼저 1~3번 문항을** 만들어 드릴까요?"입니다. 경력기술서는 "모아 둔 커리어로 바로 초안을 만들어 드릴까요?"(섹션 묶음, 프로젝트 ≤ 8개). 진행 표시의 단위도 **경력기술서 = 섹션 / 자소서 = 최대 3문항**입니다(PRD 6.4).
4. **AI-11은 사용자에게 보이는 단계입니다** (AI-4, CL-5): 첫 초안 턴 **직전 1회**(인사이트가 있으면 호출 없음) 돌고, `progress.stage = rank`로 "어떤 경력·프로젝트를 쓸지 고르는 중"을 보인 뒤 **근거 목록 카드**("이 경력·프로젝트로 쓸게요" + 이유 한 줄)를 제안 카드 앞에 보여 줍니다. **실패하면 대화가 "어느 경력·프로젝트부터 정리할까요?"를 묻습니다**(A23의 "임의 선택 금지"는 유지, 목록 화면은 없어짐). "AI에게 맡기기" / "직접 고르기" 버튼과 Q53-4 예외는 폐기입니다.
