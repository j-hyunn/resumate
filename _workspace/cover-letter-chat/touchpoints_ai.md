### 3.2 CL-6 "대화 첫 턴의 전체 초안 제안" — 토큰·지연·스트리밍

본은 AI-13의 "본문 전체 초안 제안"이지만, 서류는 **덩어리가 더 크다**.

| 항목 | AI-13 (산출물) | 경력기술서 초안 턴 | 자소서 초안 턴 (문항 3개) |
|------|----------------|---------------------|---------------------------|
| 입력 | 약 7k (사실 1.5k + 본문 0~5k + 프로젝트 1.5k) | 약 **11~17k** (경력 팩 7k~ + JD 요건 1.5k + 현재 본문 0~5k + 근거 배열) | 약 **12~15k** (팩 + JD + 소개 문장 + 문항·메모 + 현재 본문) |
| 출력 | 약 3k | 약 **5~6k** | 약 **6k** (문항 3개 × 2k) |
| 호출 | 정리 → 초안 (2) | 정리 → 초안 (2) | 정리 → 초안 → 보정 (3) |
| 지연 | 첫 블록 8초, 완료 60초 | **첫 블록 5~8초, 완료 45~70초** | **문항당 10~25초 → 3문항 40~75초** |

- **60초 제약이 자소서에서 먼저 깨진다.** 지금은 "화면이 문항별 요청을 차례로 보낸다"로 피했다(1671행). 대화형에서는 그 경로가 없다 → **초안 턴 1회에 문항 2~3개까지**로 제한하고, 남은 문항은 다음 턴에서 이어 만드는 것을 추천한다(Q-AI-1).
- **스트리밍**: AI-13의 `draft_started` → `draft_block`(블록 완료마다, 서버가 블록 단위 검증 먼저) → `draft_done`을 쓴다. 자소서는 그 앞에 `sources_selected`(문항별 근거 카드)를, 뒤에 `adjusting_length`를 끼운다. **`validated`/`draft_done`에서 블록을 통째로 교체**하는 기존 규칙(1670행)은 그대로다 — 모델 `block_id`를 화면이 믿지 않는다.
- **캐시**: 턴마다 경력 팩 + JD 요건을 다시 넣으므로 프리픽스 캐시가 핵심이다. `<document_state>`(현재 본문)는 턴마다 바뀌므로 **팩·요건 뒤**에 둔다(A-27).

### 3.3 근거 검증 V-1~V-9·숫자 가드·placeholder·글자 수가 제안 카드와 [반영] 위에서 도는 순서

1. **모델 출력 수신** (스트리밍, 블록 단위)
2. **블록 단위 1차**: V-1(ref 존재) → V-2(field 허용값) → V-3(인용 부분 문자열) → V-8(배운 점 용도) → V-7(근거 범위 = 이번 턴의 섹션 근거 배열) → 통과 블록만 `draft_block`으로 내보낸다 (AI-13 패턴)
3. **블록 단위 2차**: V-5 숫자 가드 → 위반 숫자를 `[수치 확인 필요]`로 치환 + `number_check_needed` 플래그(재생성 없음, A-16) / V-4 근거 0개 → `evidence_check_needed` 또는 `needs_review`(Q-AI-4) / V-9g·V-10f 민감정보 → 그 블록만 제거 / 스킬명 가드 → `skill_check_needed`
4. **전체 단위**: V-9j 기존 사실 보존(기존 본문 대비) → 빠진 숫자·이름이 있으면 그 섹션을 `needs_review` + `review_reason = existing_missing` / C-5 자리 표시 개수·토큰 검사 / 제거율 30% 초과면 초안 호출 1회 재실행(A-16)
5. **(자소서만) 글자 수**: 문항별 세기 → 90~110% 밖이면 `adjust_length` 호출 1회 → 다시 세기 → 밖이면 `char_adjust_needed`
6. **`draft_done`/`validated`**: 제안을 `structured_draft`에 저장, `rev` + 1. 화면은 블록을 통째로 교체
7. **제안 카드**: 섹션·문항별 목록. `needs_review` 블록은 사용자 [수락]/[빼기] (AI-13 R-PA-3 규칙)
8. **[반영]**: `review ∈ ok/accepted`인 블록만 폼에 채운다. **미수락 `needs_review`는 빠진다.** 글자 수 초과·자리 표시는 **채운다**(경고만) — 사용자가 제출 전에 고치는 것이 서류의 정상 경로
9. **"저장하기"**: 폼 값 + `p_applied_proposals`로 `applied_at`·`applied_rev` 기록(한 트랜잭션). `skipped` 사유는 AI-12·AI-13과 같은 목록

| **Q-AI-6** | AI-12·AI-13의 공통 문구를 **이 사이클에서** `chat-common` 블록으로 뺄까? 빼면 두 기능의 `prompt_version`이 올라가고 평가 세트를 다시 돌려야 한다 | **이 사이클에서는 빼지 않는다.** C-15 공통 규칙 절은 **문서 구조로만** 만들고(세 카드가 참조), 프롬프트 바이트는 기능별로 둔다. 이유: AI-12·AI-13은 구현·검증이 끝난 기능인데 서류 대화 때문에 회귀 평가를 다시 돌리는 비용이 크다. 서류 대화가 안정된 뒤 별도 작업으로 묶는다 |
| **Q-AI-7** | CL-A3의 **tone**(문체)을 프롬프트에 어떻게 넣을까? 화면 선택이 없어지고 "대화에서 지시한 마지막 값"이다 | **정해진 값 2개(`concise`/`detailed`)를 유지**하고, 정리(extract) 호출이 발화에서 그 값을 뽑아 `structured_draft` 메타에 쓴다(AI-13의 `style`·`writing_kind` 판정과 같은 방식). **자유 텍스트 지시를 프롬프트에 그대로 넘기지 않는다**(C-4 "사용자 입력은 정해진 값만"). "더 격식 있게"처럼 두 값에 안 맞는 지시는 그 턴의 초안 지시로만 쓰고 메타에 저장하지 않는다 |
| **Q-AI-8** | 경력기술서 대화의 **질문 슬롯**을 무엇으로 정할까? AI-12는 STAR 5필드, AI-13은 종류별 5슬롯 | **경력·프로젝트가 슬롯이다** — `focus_slots = [{experience_ref, project_ref}]`. 각 슬롯의 구체 요소는 "본인 행동 / 결과 수치 / JD 요건과의 연결". 근거가 되는 STAR는 커리어 데이터에 이미 있으므로, 대화는 **STAR를 다시 묻지 않고** "이 프로젝트를 이 JD에 어떻게 보일까"를 묻는다. STAR 자체가 비면 AI-12(프로젝트 상세)로 보낸다 — 게이트 진입의 역방향 |
| **Q-AI-9** | `omitted`·`notes_for_user` 미저장(A21)은 대화형에서 어떻게 되나? 지금은 "`validated` 이벤트에서만 보인다" | **AI 메시지 본문으로 바꾼다** — 대화에는 메시지가 있으므로 "'정산 배치 개선'은 결과에 수치가 없어 자리 표시를 넣었어요"를 초안 턴의 고정 문구 AI 메시지에 담으면 **다시 열어도 보인다**. A21의 "저장하지 않는다"는 `drafts` 전제였고, 대화 기록이 그 자리를 대신한다. A21을 8장 "해소"로 옮긴다 |
